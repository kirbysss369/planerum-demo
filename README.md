# Планерум

Проект команды `tochka-sborki-2026-team-020`. Рабочее место методиста для подготовки образовательных программ. Планерум связывает результаты обучения, темы, часы и оценочные материалы, хранит версии и собирает документы из одних данных.

Подготовка программы вручную по условиям кейса занимает 2–8 недель. Цель проекта — сократить составление документов и повторные проверки их согласованности. Методист проверяет и утверждает каркас, затем получает материалы для доработки и выгрузки.

**Текущий выпуск — прототип с реальной генерацией через разрешённый GigaSchool gateway.** Рабочий режим использует PostgreSQL и требует ключ модели и сервисный токен. Отдельный демонстрационный режим работает без внешних ключей с заранее заданным тестовым содержанием. Реальный комплект остаётся черновиком для проверки методистом; запуск сервиса не означает полную приёмку продукта.

Для реальной генерации используйте [рабочий режим](#рабочий-режим-с-реальной-моделью). Демо ниже предназначено для проверки процесса без ключей и расходов.

## Локальная проверка без модели (демо)

Нужен Docker с Compose. Из каталога проекта:

```bash
docker compose -f compose.demo.yaml up --build
```

Откройте [127.0.0.1:8080](http://127.0.0.1:8080). Поле токена в локальном демо можно оставить пустым. Программы и очередь хранятся в памяти и исчезают при перезапуске, выгрузки сохраняются в Docker volume.

Остановка:

```bash
docker compose -f compose.demo.yaml down
```

## Сценарий показа: 3–5 минут

1. Опишите курс свободным текстом, например: «Анализ банковских данных на Python», повышение квалификации, 72 часа, банковские аналитики, начальный уровень Excel, очно-заочная форма, защита проекта.
2. Отправьте запрос и ответьте на уточнения. В разделе «Условия курса · редактировать» проверьте извлечённые поля. При необходимости загрузите DOCX, PDF с текстовым слоем или TXT; проверьте извлечённый текст в требованиях. Для больших референсов сначала завершите уточнения, затем добавьте документы перед подготовкой каркаса.
3. Нажмите «Подготовить каркас». Покажите цель, карту знаний, умений и навыков, учебно-тематический план и баланс часов.
4. Утвердите каркас отдельной кнопкой и запустите подготовку материалов. До утверждения генерация и экспорт недоступны.
5. Покажите тест с ответом, практическое задание с критериями и план лекции. Нажмите «Собрать файлы»: доступны DOCX, PPTX, Moodle XML, JSON и отчёт проверок одной версии.
6. Измените ответ теста: версия увеличится, утверждение сохранится. Изменение темы отменит утверждение; в текущей версии оно также удаляет все подготовленные материалы.
7. Нажмите «Новый запрос» и опишите другую программу без части условий. Появятся уточняющие вопросы; прежний комплект не будет отображаться как результат нового запроса. Откройте сохранённый черновик по его идентификатору, чтобы продолжить обсуждение.

В демо показывается работа приложения. Пригодность учебного содержания и источников проверяет методист; статус готового комплекта означает готовность к этой проверке.

## Нормативные привязки, адаптация и оценка прогонов

В интерфейсе и отчёте показываются основания для выбранного типа программы: 273-ФЗ и порядок № 266 для повышения квалификации, 273-ФЗ и порядок № 629 для общеразвивающих программ. Реквизиты справочника подобраны 23.10.2026; актуальность редакций и применимость требований проверяет методист. Упомянутый в исходном кейсе приказ № 499 не используется как текущий порядок вместо № 266.

В разделе «Привязка к профстандарту» методист выбирает результат обучения, указывает точный код трудовой функции, адрес источника и проверенный фрагмент с этим кодом. Подтверждение человеком обязательно. Привязка и изменение её основания снимают утверждение: каркас проверяется заново, материалы готовятся после нового утверждения. API-действие — `bind_standard` с `program_id`, `revision` и объектом `binding`: `outcome_id`, `code`, `title`, `location`, `evidence`, `confirmed`. Ссылки на отсутствующие источники и коды, которых нет в фрагменте, отклоняются. Это проверка предоставленного основания, а не автоматическое подтверждение в реестре профстандартов.

Для актуализации или новой аудитории откройте готовую программу, опишите изменения и нажмите «Адаптировать копию». Действие `adapt` с `program_id`, `revision`, `message` создаёт отдельный черновик с референсом исходного каркаса. Исходная программа сохраняется; её утверждение и материалы в копию не переносятся.

Для новых вызовов измерения содержат режим `real`/`demo`, модель, конфигурацию, хеши инструкции, входа, ответа и схемы, время и токены. У исторических записей режим может быть `unknown`, у смешанной истории — `mixed`; они не выдаются за подтверждённые реальные прогоны. Ключи и полные запросы в измерения не включаются. Ответы 429/502/503/504 допускают один повтор с отдельным учётом попытки; при Retry-After дольше двух секунд сервис возвращает ошибку недоступности без ожидания и повтора. Тайм-ауты и ошибки разбора платного ответа автоматически не повторяются. Если провайдер не сообщил usage неуспешной попытки, это помечается как неизвестный расход, а не подтверждённый ноль. Отчёт `validation-report.json` содержит эти данные и нормативные привязки.

Сравнение независимых выгруженных программ выполняется без новых вызовов модели:

```bash
go run ./cmd/evaluate -out data/evaluation.json data/run1/program.json data/run2/program.json
```

Оценка считает структурную полноту, покрытие, подтверждённые привязки, время и токены. Для повторов одного входа и конфигурации показывает долю структурно успешных результатов, разброс времени и токенов; демо и реальные данные разделены. Проверяются цели 180 секунд на каркас и 1200 секунд на материалы программы в 72 часа. Это не оценка педагогического качества и не гарантия дословного совпадения ответов модели.

## Что предстоит завершить

- Правки готового каркаса и материалов произвольными текстовыми командами: пока они редактируются через поля интерфейса и API `revise`. Свободный диалог работает на этапе сбора условий.
- Календарь и отдельные проверки количественных условий: числа вопросов, минимальной практики, дневной нагрузки и состава слайдов.
- Все разделы обоих шаблонов АЦР и автоматическую сверку актуальности источников с внешними реестрами; привязки кодов к подтверждённым методистом фрагментам проверяются уже сейчас.
- Выборочную перегенерацию зависимых материалов и сохранение завершённых частей при сбое.
- Дополнительные реальные прогоны по исходным открытым запросам, проверку прямого маршрута Cloud.ru, импорт в LMS и методическую приёмку.

Числа 3 минуты на каркас и 20 минут на комплект 72 часа — целевые показатели кейса. Результаты отдельных прогонов не подтверждают экономию труда методиста или устойчивое достижение целей на новых запросах. Ни один открытый запрос не объявлен прошедшим продуктовую приёмку только по результатам демо.

## Свободный запрос через API

Все действия выполняются через `POST /v1/agent` с Bearer-токеном рабочего экземпляра. Начало обсуждения:

```json
{"action":"intake","message":"Нужна программа повышения квалификации по анализу банковских данных на Python, 72 часа, для сотрудников банка."}
```

Ответ содержит `program` в состоянии `draft`, его `id`, `revision`, извлечённый `spec`, сохранённый `dialogue` и `questions`. Неизвестные поля остаются пустыми. Уточнение передаётся с актуальной ревизией:

```json
{"action":"answer","program_id":"<id из ответа>","revision":1,"message":"Слушатели владеют Excel, Python не знают. Форма очно-заочная, аттестация — защита проекта. Персональные данные не использовать."}
```

Даже после заполнения всех полей программа остаётся черновиком. После проверки параметров отдельно отправьте `create` с теми же `program_id`, актуальной `revision` и полным подтверждённым `spec`. Каркас получает тот же ID и новую ревизию; затем требуется отдельное `approve_outline`. `status` восстанавливает сохранённые условия, историю и вопросы. Поле `spec` в `intake`/`answer` необязательно и позволяет передать отредактированные условия и референсы; при его отсутствии используются сохранённые параметры. Для совместимости прежний `create` с одним `spec` и `answer` без сообщения и ID продолжают работать.

В API сообщение ограничено 8 000 символами, в интерфейсе — 4 000. Диалог ограничен 20 сообщениями пользователя и 64 000 символами суммарного контекста; требования и референсы — 64 000 символами. Длинный ответ модели может упереться в лимит токенов: в таком случае возвращается ошибка, без подмены демо-содержанием. Сохранённый черновик и возвращённый usage доступны в ответе ошибки; используйте новую ревизию для повтора. Учёт usage не подтверждает биллинг провайдера. Параллельные запросы используют проверку ревизии; проигравший конфликт может уже израсходовать токены модели.

В явном деморежиме разбор офлайн распознаёт ограниченный набор формулировок правилами. Это проверка процесса, а не оценка качества языковой модели; данные памяти пропадают при перезапуске.

## API

Основной маршрут — `POST /v1/agent`. Создание программы из примера:

```bash
curl --fail-with-body http://127.0.0.1:8080/v1/agent \
  -H 'Content-Type: application/json' \
  --data-binary @examples/bank72.json
```

Действия: `intake`, `create`, `answer`, `status`, `approve_outline`, `generate`, `generate_async`, `job_status`, `revise`, `export`. Для изменения программы передаются `program_id` и текущий `revision`; устаревшая версия возвращает HTTP 409. Генерация или экспорт до утверждения — HTTP 422.

`POST /v1/references` принимает multipart-поле `file`. `GET /healthz` проверяет доступность процесса. При заданном `SERVICE_TOKEN` маршруты `/v1/agent`, `/v1/references` и скачивание `/artifacts/` требуют заголовок `Authorization: Bearer <токен>`. Маршрут `/api/v1/hours/validate` открыт без токена. Подробный контракт — [OpenAPI](docs/openapi.yaml).

В интерфейсе, DOCX и `validation-report.json` доступна матрица «компетенция → темы → тестовые вопросы → практические задания». Проверяются идентификаторы и взаимность связей; соответствие содержания компетенциям проверяет методист.

В интерфейсе и JSON-отчёте сохраняются длительность и токены каждой попытки разбора запроса, построения каркаса и генерации материалов, включая ошибки. Время относится только к записанным этапам; у старых программ измерения могут отсутствовать.

Загрузки ограничены 10 МиБ, DOCX — 64 МиБ распакованных данных и 2000 элементов, PDF — 100 страницами. Документы с макросами, вложенными архивами и активным содержимым отклоняются. Обработка ограничена 30 секундами, сборка файлов — двумя минутами.

## Разработка и проверки

Без Docker:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r office/requirements.txt
DEMO_MODE=1 OFFICE_PYTHON="$PWD/.venv/bin/python" go run ./cmd/server
```

Проверки:

```bash
go vet ./...
OFFICE_PYTHON="$PWD/.venv/bin/python" go test -race -count=1 ./...
.venv/bin/python -m unittest discover -s office -p 'test_*.py'
for file in static/*.js; do node --check "$file" || exit 1; done
```

Office-тесту нужны Python-зависимости. Для проверки PostgreSQL задайте `TEST_DATABASE_URL` отдельной тестовой базы; без него тест пропускается.

Для повторения HTTP-проверки запустите отдельное демо:

```bash
DEMO_MODE=1 PORT=18080 SERVICE_TOKEN=local-release-token \
  OFFICE_PYTHON="$PWD/.venv/bin/python" go run ./cmd/server
```

В другом терминале:

```bash
SERVICE_TOKEN=local-release-token python3 scripts/release_check.py \
  --demo --base http://127.0.0.1:18080 --out data/release-check
```

Флаг `--demo` подтверждает, что выбран демонстрационный сервер; режим самого сервера он не меняет. Результаты и выгрузки сохраняются в указанном каталоге и не включаются в Git.

## Рабочий режим с реальной моделью

Скопируйте `.env.example` в `.env` и заполните пароль PostgreSQL, `SERVICE_TOKEN`, ключ модели, её ID и явный список `CLOUD_ALLOWED_MODEL_IDS`. Поддержаны прямой Cloud.ru (`https://foundation-models.api.cloud.ru/v1`) и GigaSchool (`https://hub.gigaschool.ru/api/v1/llm/v1`); для GigaSchool допустима только `GigaChat/GigaChat-3-Pro`. Ключ должен соответствовать выбранному маршруту. Значения ключей и `.env` не публикуются.

```bash
cp .env.example .env
chmod 600 .env
# Заполните .env перед запуском.
docker compose --env-file .env config --quiet
docker compose --env-file .env up --build -d
```

По умолчанию приложение доступно на `127.0.0.1:8080`. Адрес и порт задаются через `APP_BIND_ADDRESS` и `APP_PORT`. В интерфейсе нужен сервисный токен. Это общий токен экземпляра: разграничения программ по пользователям и SSO пока нет. `/healthz` проверяет только HTTP-процесс, без проверки базы и модели.

Программы и очередь сохраняются в PostgreSQL, выгрузки — в Docker volume. `docker compose down` сохраняет данные, `down -v` удаляет их. Перед обновлением нужна согласованная резервная копия базы и выгрузок; восстановление и обратные миграции автоматически не выполняются.

Вызовы реальной модели, включая `scripts/smoke.py`, расходуют токены. `CLOUD_MAX_RESPONSE_TOKENS` ограничивает ответ отдельного запроса, а не стоимость прогона; слишком низкое значение может оборвать JSON. При ошибке материалы целиком не сохраняются, повторная подготовка заново вызывает модель. Время и доступный usage отражаются в отчёте; фактическую стоимость проверяют по тарифу и биллингу провайдера.

`EMBED_MODE=1` скрывает повторный логотип при встраивании. Интеграция с авторизацией хоста требует отдельного согласования.

## Материалы и права

Открытая лицензия на код не выбрана. Лицензии зависимостей действуют отдельно.

Логотип и CSS-переменные GigaCowork взяты из предоставленного проекту набора визуальных материалов, основанного на [сайте GigaCowork](https://cowork.ru/) и [документации платформы](https://cowork.ru/docs/). Их соответствие внутреннему брендбуку компании ещё не подтверждено. Обозначения принадлежат правообладателю; брендовые шрифты в репозитории не распространяются.

Исходные программы АЦР, пользовательские документы, `.env`, ключи доступа, локальная база и выгрузки из `data/` не публикуются.
